
## 太阳系总览重构（对齐 solar-system-atlas）

**根因**：参考站默认 `positionMode: SCHEMATIC` —— 行星不按真实历表，而是按压缩轨道距离排在
+X 一条线上再 ×0.46（图谱排布）。前几轮一直用真实轨道去拟合它的截图，所以永远有残差。
另外旧相机是 fov60 透视 + `mesh.scale = clamp(R*30000/dist,1,30)` 的按距离放大 hack，两者叠加使构图必然不像。

**取真值的方式**（下次直接用）：打开 `https://solar-system-atlas.pages.dev/solar/?debug=1`，
调 `window.__atlasStore.getState().enterAtlas()` 进图谱，再调 `window.__atlasCamera()` 读
target/height/yaw/pitch。bundle 里还有 `window.__atlasLayout / __atlasPerf / __atlasSkyState`。
bundle: `curl -s https://solar-system-atlas.pages.dev/solar/assets/solar.js -o /tmp/atlas/solar.js`，
关键函数：`er`(距离表) `VG`(半径) `jye`(排布) `aee`(相机) `Mg/Rg`(带边界) `Zs`(体量档位)。

**实测值**：视宽 197.8、视心 91.08、可视高 128.465(@1512×982)、指数排布 ×0.46、
半径 0.0115·km^0.42、缩放 exp(dy·0.0011) 限 0.45–1520、pitch 限 ±1.35。

**改动**：js/flight.js 整体重写为 rig（target/viewHeight/yaw/pitch）；main.js 打开即进总览；
solar.js 去掉全部距离缩放、补柯伊伯带+奥尔特云；地球云层改 alphaMap（原来灰度 JPG 当 map
把地表盖住，一直"发白"）；starfield.js 补回被误删的 `group.add(sky)`。

**验证**：地球世界坐标 (36.80,0.24) vs 参考站 (36.799,0.2415)；屏幕位置 太阳 x=60、
水星 172、地球 341、木星 678（1512 宽），与正交投影推算逐像素一致。

## 轨道线贴合 + 知识内容扩充

**轨道线"分离"的两个根因**（下次直接照这个公式）
1. `orbitPointsFrom` 半径写成 `auToScene(p)`，但位置函数 `bodyPosition` 用的是
   `auToScene(a) × (p/a)`。`auToScene` 是分段线性压缩，两者不等价 → 离心率大的
   天体（火星 e=.093、彗星 e=.53~.97、天王星/海王星）轨道圈内缩，行星"跑出轨道"。
   修法：`hU = auToScene(el.a) * ratio * SCHEMATIC`，与位置同源。
2. 采样密度：256 段时相邻点间距近 2 个世界单位（总览 7.65 px/单位 ≈ 15px 缝）。
   提到 3000 段后最大偏差 0.128 单位 ≈ 1px。

**示意排布模式的轨道线**：行星被摆在压缩半径的直线上，画真实椭圆必然错位。
改成同心导轨（`ringPoints(auToScene(a)*SCHEMATIC)`），圈精确穿过行星（误差<0.001）。
`solar._syncOrbitMode()` 按 `positionMode` 切换两套几何；彗星 `orbitAlways: true`
两种模式都显示真实椭圆。

**知识内容**
- `data.js` 新增：`BLURB`（行星一句话提要，挂 p.desc）、`FACTS`（按 id 索引的冷知识，
  模块加载时挂到 PLANETS / MOONS[].info / COMETS[].info / SUN_INFO）、
  `ARTICLES`（9 篇知识库文章，字段 id/cn/en/kicker/lead/stats/sections）。
- 行星球新增第 4 节「怎样看到它」；卫星与彗星分节补到 2–3 节。
- `ui.js`：`_buildKnow/showKnow/showArticle` + 顶部「知识」标签页；
  档案卡补 `#pc-sub`（提要）、`.pc-explore` chips（`_exploreChips`）、
  `#pc-facts`（冷知识）、`#pc-src`（资料来源，对应目录最后一项）。

⚠️ 写中文内容进 data.js 时，Python 脚本里的 ASCII 双引号会截断字符串，
   统一用中文引号「“ ”」，或把插入点放在整个 `{...}` 之后（别插在字符串闭合与 `}` 之间）。

**踩过的坑（很重要）**：`obj.visible = a && b` 在 b 为 undefined 时得到 `undefined`，
而 three.js 只把 `visible === false` 当隐藏 —— 于是"隐藏"没生效，两套轨道线同时画，
画面里全是扫过全屏的弧线。凡是要控制显隐，一律 `!!(...)` 布尔化。

## 背景"被放大"的真相：FOV 不是构图参数

构图基准是 `flight.viewHeight`，`_dist = viewHeight / (2·tan(fov/2))`。
也就是说 **改 FOV 只改变相机站位，不改变目标平面上的构图**（行星屏幕位置分毫不动），
但天球背景在无穷远 —— **FOV 一变，银河/星点的视觉尺寸就跟着变**。
我早期为了模仿参考站的正交感把 FOV 从 60 收到 40，等于把整个背景放大了 1.6 倍，
用户看到的就是"银河被拉近了"。

修法：`main.js` 的 `fovForVH(vh)` 按视高分两档 ——
特写(<40) 40°、总览(≈128) 60°、深空(>4000) 40°（深空刻意保留大银河）。
`flight.fovForVH` 注入后，`_poseFrom` 用 3 次迭代解 vh↔fov 的互相依赖，
`update()` 里在 `_applyCamera()` **之前**改 fov（否则距离用的是旧 fov）。

验证：总览行星屏幕 x = 60/172/340/678/1292（1512 宽），与改动前逐像素一致；
特写地球占半屏 0.531；深空 vh 10727 与改动前相同。

## 拖拽语义统一 + 深空解除地平限位

**语义**：统一成"抓住天空拖"——往哪拖天空往哪走。横向 `_tYaw += dx*k`，
纵向必须 `dp = -dy*k`（早期是 `+=`，结果往下拖银河往上跑）。
**惯性也要同号**：`_inertia.pitch += ((-dy)*k/dtm - ...)`，
否则松手会被惯性往反方向拽回去（实测 120px 下拖先 -0.29 再被拉回 +0.4）。

**深空自由俯仰**：`flight.freePitch`（main 在 goDeep 设 true，回太阳系设 false）。
为 true 时不 clamp pitch，`_applyCamera` 改用 `Euler(-pitch, yaw, 0, 'YXZ')`
构造四元数 —— `lookAt` + 固定 up 在 |pitch|>90° 会万向锁翻转。
在 |pitch|<90° 时两者数学等价（已核对），所以太阳系构图不受影响。
`applyPitchLink` 在 freePitch 时直接 return（深空不做缩放联动俯仰）。

**验收数据**（1512×982，拖 120px）：太阳系下拖 → 背景下移 567px；
右拖 → 背景右移 769px；深空上拖 160px → 上移 696px，pitch 可累加到 7.2 rad。
